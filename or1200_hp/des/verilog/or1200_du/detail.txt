1. Internal state and register bank
A reimplementation must preserve the existence and function of the following logical register classes.
- DMR1 and DMR2: mode/control registers enabling stop conditions and watchpoint combinations.
- DSR: Debug Stop Register, selects which events cause a stop.
- DRR: Debug Reason Register, accumulates which event actually caused the stop.
- DVR0..DVR7: debug value registers used as comparison operands.
- DCR0..DCR7: debug control registers describing comparison type, source, and chain/qualifier behavior.
- DWCR0/DWCR1: watchpoint counter registers when enabled.
- optional trace-buffer related registers if the relevant feature macros are present.
The module is heavily feature-parameterized through defines. When a feature macro is absent, the corresponding register reads as zero or the functionality is reduced.

2. Functional behavior
2.1 Status pass-through and simple visibility
The module drives external summarized activity outputs. For example, dbg_lss_o reflects whether LSU is active and whether it is a write. dbg_is_o reflects instruction fetch activity. These are not full traces; they are compact activity indicators.

2.2 External debug port handshake
dbg_ack_o is generated as a delayed acknowledgment of dbg_stb_i. The handshake is intentionally simple rather than fully Wishbone-compatible. Reads and writes from the external debug interface are translated into du_read/du_write plus du_addr/du_dat_o toward the processor-side access path.

2.3 Processor stall generation
du_stall is asserted when debug mode requires the core to stop. Sources include:
- external stall request;
- internal breakpoint/watchpoint logic;
- exception stop conditions selected in DSR/DMR.
The design distinguishes between a momentary event (for example a breakpoint hit) and sustained stall state driven by dbg_stall_i or by latched debug behavior.

2.4 Exception stop decoding
The source contains logic that decodes the one-hot/priority-coded du_except input into a Debug Reason Register bit vector called except_stop. Each exception category maps to a DRR reason bit such as tick timer exception, interrupt exception, ITLB miss, instruction page fault, bus error, illegal instruction, alignment exception, DTLB miss, data page fault, reset, trap, or syscall. The module then:
- records the reason in DRR;
- uses the same reason vector as an input to breakpoint/stop generation.

2.5 Breakpoint event generation
dbg_bp_o is a registered breakpoint output. The module updates dbg_bp_r when a selected stop reason occurs. It may also treat certain instruction classes or branch events as stop sources when enabled by DMR1 bits. If OR1200_DU_HWBKPTS is enabled, programmable match conditions on addresses/data/instruction state participate in breakpoint generation.

2.6 Watchpoint comparator architecture
A faithful reimplementation should model eight comparator channels. Each channel has:
- one DVR value register;
- one DCR control register.
The DCR selects what the comparator examines (for example address, data, fetch stream, or other event class) and what comparison type is used. Match outputs can be combined under DMR1/DMR2 policies into final watchpoint outputs. The code includes per-channel match registers, per-channel counters/qualifiers, and final wp vector generation when hardware breakpoints are enabled.

2.7 DRR and DSR semantics
- DSR is programmable by SPR writes and determines which classes of events are considered stop-worthy.
- DRR accumulates the reasons that actually occurred; it is writable from SPR for software clear/maintenance but also ORs in new exception-stop causes automatically.
This separation is important: DSR is policy, DRR is history/cause.

2.8 Register access via SPR
Each named debug register has an address decode using spr_addr[10:0]. On write, the selected internal register loads spr_dat_i. On read, spr_dat_o returns the selected register contents with appropriate zero-padding for unimplemented bits.

3. Optional trace-buffer behavior
The source includes optional trace-buffer support behind feature defines. A compatible implementation may either implement the trace buffer exactly or clearly omit it when the corresponding feature macro is absent. If implemented, it records timestamped activity such as instruction address, instruction word, ALU result, and timing/state metadata.

4. Implementation rules
A new implementation must preserve these observable properties:
- debug register map and read/write semantics;
- external debug handshake behavior (stb -> ack, read/write direction, data routing);
- stall and breakpoint outputs generated from selected stop reasons;
- exception-to-DRR reason decoding;
- configurability through feature defines;
- separation between policy registers (DMR/DSR) and captured reasons/events (DRR/wp/bp).

5. Summary
or1200_du.v is the run-control and event-observation hub of the core. It is not just a passive register bank; it continuously classifies processor activity and turns programmable conditions into stalls, breakpoints, and debug-visible state.
