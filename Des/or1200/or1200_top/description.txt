or1200_top is the top-level integration module of the OR1200 processor system. Its main responsibility is not to implement new execution logic, cache protocols, or bus state machines at the top level, but to declare the system-level input and output ports, define internal interconnect signals, and instantiate and connect the CPU core, Instruction/Data Wishbone BIUs, IMMU, DMMU, Instruction Cache, Data Cache, QMEM, Store Buffer, Debug Unit, Programmable Interrupt Controller, Tick Timer, Power Management Unit, and the optional MBIST chain. Through the composition of these submodules, this module forms a complete OR1200 processor subsystem.

This module uses clk_i as the top-level system clock and rst_i as the top-level reset signal. The Instruction Wishbone BIU and Data Wishbone BIU retain the structural form of separate Wishbone clock/reset interfaces, but in the current implementation, both iwb_clk_i and dwb_clk_i are directly tied to clk_i, and both iwb_rst_i and dwb_rst_i are directly tied to rst_i. Therefore, according to the current top-level code, the instruction-side and data-side Wishbone BIUs operate in the same top-level clock/reset domain as the processor core. The clmode_i signal is passed to the instruction and data Wishbone BIUs to indicate the clock mode or clock-division relationship between the Wishbone side and the RISC side.

On the instruction access path, the CPU issues instruction-fetch-related address, control, select, and tag signals through its instruction-side interface. These signals, together with the IMMU, QMEM, Instruction Cache, and Instruction Wishbone BIU, form the instruction-fetch access path. The IMMU participates in instruction address translation, exception handling, retry control, and tag-related control. QMEM is located between the CPU/IMMU side and the Instruction Cache side, connecting the on-chip fast-memory-related path with the cache access path. When an external bus access is required, the Instruction Cache initiates the external Wishbone transaction through the Instruction Wishbone BIU. The top-level module itself does not implement instruction-fetch arbitration or cache hit logic; those behaviors are implemented inside the corresponding submodules.

On the data access path, the CPU issues data access requests through its data-side interface, including address, read/write control, byte select, tag, and write-data signals. The DMMU participates in data address translation, exception handling, and cacheability/tag-related control. QMEM connects the data access path between the CPU/DMMU side and the Data Cache side. The Data Cache is then connected to the Data Wishbone BIU through the Store Buffer. The Store Buffer sits between the Data Cache and the Data Wishbone BIU, where it buffers or forwards data-side accesses to the external Wishbone bus. It is important to note that the DMMU does not simply pass the complete data bus through; it mainly handles address, exception, tag, and control information. The actual data path is formed by the signals between the CPU, QMEM, Data Cache, Store Buffer, and Data Wishbone BIU.

This top-level module also connects the SPR access path generated by the CPU. The CPU outputs the unified spr_addr, spr_dat_cpu, spr_we, and spr_cs signals, and receives the corresponding spr_dat_* return data from the functional units. For the IMMU, DMMU, Instruction Cache, Data Cache, Debug Unit, PIC, and Tick Timer, the top level uses different bits of spr_cs to generate the corresponding group select signals. For example, spr_cs[2] selects the IMMU, spr_cs[1] selects the DMMU, spr_cs[4] selects the Instruction Cache, spr_cs[3] selects the Data Cache, spr_cs[6] selects the Debug Unit, spr_cs[9] selects the PIC, and spr_cs[10] selects the Tick Timer. In the current code, the Power Management Unit does not have an explicitly connected separate spr_cs group select signal. Instead, it directly receives spr_write, spr_addr, and spr_dat_i, and outputs spr_dat_pm.

Interrupt-related signals are also connected at the top level. The external interrupt input pic_ints_i is routed to the Programmable Interrupt Controller. Based on the external interrupt inputs and SPR configuration, the PIC generates the overall interrupt request sig_int and outputs pic_wakeup as a power-management-related wakeup signal. The Tick Timer generates sig_tick and sends it to the CPU. As a result, the CPU can receive both external interrupt requests from the PIC and timer interrupt requests from the Tick Timer.

The debug interface is connected and handled by the or1200_du Debug Unit. The external debug port includes dbg_stall_i, dbg_ewt_i, dbg_stb_i, dbg_we_i, dbg_adr_i, dbg_dat_i, and the corresponding debug output signals. The Debug Unit connects to the external dbg_* interface on one side and interacts with the CPU through internal signals such as du_stall, du_addr, du_dat_du, du_read, du_write, du_except, and du_hwbkpt on the other side. These signals support debug stall, debug access, exception control, and hardware-breakpoint-related functions. The top level only connects these debug signals; the specific debug behavior is implemented inside the Debug Unit and the CPU.

The Power Management Unit receives the top-level input pm_cpustall_i, the pic_wakeup signal from the PIC, and related control signals from the CPU/SPR access path. It outputs multiple power-management control signals, including pm_clksd_o, pm_dc_gate_o, pm_ic_gate_o, pm_dmmu_gate_o, pm_immu_gate_o, pm_tt_gate_o, pm_cpu_gate_o, pm_wakeup_o, and pm_lvolt_o. These signals are used to express clock slowdown, clock gating, wakeup, and low-voltage request states to external system logic or downstream blocks. The top level does not directly execute the power-management policy; it connects the relevant inputs and outputs to the or1200_pm module.

The Instruction Wishbone interface and Data Wishbone interface are responsible for instruction-side and data-side external bus accesses, respectively. The Instruction Wishbone BIU connects the Instruction Cache to the external iwb_* ports. The Data Wishbone BIU connects the Data Cache to the external dwb_* ports through the Store Buffer. Wishbone handshake and termination signals such as ack, err, and rty are received by the corresponding BIU and fed back into the internal access path. If OR1200_WB_CAB is enabled, the top level additionally exports iwb_cab_o and dwb_cab_o. If OR1200_WB_B3 is enabled, the top level additionally exports iwb_cti_o, iwb_bte_o, dwb_cti_o, and dwb_bte_o. These ports are controlled by conditional compilation and exist only when the corresponding macro definitions are enabled.

When OR1200_BIST is enabled, the top level also connects the RAM MBIST scan chain. The MBIST input mbist_si_i first enters the IMMU, then passes through the Instruction Cache, QMEM, DMMU, and Data Cache in sequence, and finally exits through mbist_so_o. The chain order is mbist_si_i → IMMU → IC → QMEM → DMMU → DC → mbist_so_o. If OR1200_BIST is not enabled, these MBIST ports and internal scan-chain connections are not present in the compiled module.

Overall, or1200_top is a system-level integration wrapper. It preserves the external system, Wishbone, debug, interrupt, BIST, and power-management interfaces of the OR1200, while internally connecting the CPU, caches, MMUs, on-chip memory access path, external bus access path, debug logic, interrupt logic, timer, and power-management logic. The module itself contains no explicit always blocks, local registers, or independent state machines; timing state and protocol behavior are mainly implemented by the instantiated submodules. The current code also does not contain additional multi-clock-domain inputs, clk_i_cml_* signals, or CMLS memory-steering logic, so those features should not be described as functionality implemented by this file.

Processing Flow

At a high level, or1200_top does not define a single sequential processing flow by itself. Instead, it defines several parallel access and control flows by wiring together the OR1200 submodules. The actual timing, arbitration, cache behavior, exception handling, and bus protocol behavior are implemented inside the instantiated submodules.

For instruction fetches, the CPU issues instruction-side request signals, including address, control, select, and tag information. These signals are processed through the IMMU-related path for instruction address translation and exception/tag control, then connected through QMEM and the Instruction Cache path. If the requested instruction cannot be served internally, the Instruction Cache accesses the external instruction Wishbone bus through the Instruction Wishbone BIU.

For data accesses, the CPU issues data-side address, read/write control, byte select, tag, and write-data signals. The DMMU participates in address translation, exception generation, and cacheability/tag control. QMEM connects the CPU/DMMU side to the Data Cache side. Data-side accesses that need to reach the external bus pass through the Data Cache, then the Store Buffer, and finally the Data Wishbone BIU before appearing on the external dwb_* interface.

For SPR accesses, the CPU generates the shared SPR address, write enable, write data, and chip-select signals. The top level routes these signals to different functional blocks, such as the IMMU, DMMU, caches, Debug Unit, PIC, and Tick Timer, using group-qualified spr_cs bits. Each selected block may return its corresponding spr_dat_* value back to the CPU/SPR path. The Power Management Unit also participates in the SPR-related control path, although in this code it is not selected through an explicit top-level spr_cs group signal.

For interrupt and timer events, external interrupt inputs are sent to the PIC, which generates the CPU interrupt request and wakeup-related signal. The Tick Timer independently generates the timer interrupt signal. Both interrupt sources are connected back to the CPU, allowing the CPU to respond to external interrupt events and timer events.

For debug operation, the external debug interface is connected to the Debug Unit. The Debug Unit exchanges stall, access, exception, and breakpoint-related signals with the CPU, allowing external debug logic to observe or control processor execution through the debug path.

For power management, the Power Management Unit receives CPU stall information, PIC wakeup information, and SPR-related control signals. It produces clock slowdown, clock gating, wakeup, and low-voltage request outputs. The top level only connects these signals; the actual power-management policy is handled inside the Power Management Unit.

If MBIST is enabled, the top level also connects the MBIST scan flow. The scan input enters the IMMU and then passes through the Instruction Cache, QMEM, DMMU, and Data Cache before reaching the MBIST scan output.
