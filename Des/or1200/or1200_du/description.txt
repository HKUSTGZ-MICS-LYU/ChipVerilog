Module or1200_du implements the OR1200 debug unit. It connects the external debug interface, the CPU-internal debug access interface, and the SPR-based debug register interface. Its main functions are external debug access forwarding, debug register storage and access, exception-stop decoding, breakpoint indication, hardware watchpoint comparison, optional watchpoint counters, and optional trace-buffer recording.

At the basic interface-bridging level, several signals pass directly through the debug unit. The external debugger can request a CPU stall through dbg_stall_i, and du_stall is directly assigned from this signal. External debug address/data accesses are converted into internal debug access signals: du_addr is driven by dbg_adr_i, du_dat_o is driven by dbg_dat_i, du_read is asserted when dbg_stb_i is high and dbg_we_i is low, and du_write is asserted when both dbg_stb_i and dbg_we_i are high. Read data from the CPU-internal debug path is returned directly through dbg_dat_o = du_dat_i. The external acknowledge signal dbg_ack_o is a registered, one-cycle delayed version of dbg_stb_i, cleared to 0 on reset.

The module also exports simple processor-status information to the external debug interface. When OR1200_DU_STATUS_UNIMPLEMENTED is not defined, dbg_lss_o reflects data-side LSU activity and whether the access is a write, while dbg_is_o reflects instruction-fetch activity. When status support is marked unimplemented, dbg_lss_o is fixed to 0 and dbg_is_o is generated by a small temporary activity-toggle mechanism. In this implementation, dbg_wp_o is always assigned 11'b000_0000_0000; therefore, although the module may internally compute watchpoint bits wp[10:0], the actual external dbg_wp_o port does not report those internal watchpoint hits.

When OR1200_DU_IMPLEMENTED is enabled, the module implements a set of debug registers, depending on compile-time configuration macros. These include DMR1 and DMR2 debug mode registers, DSR debug stop register, DRR debug reason register, up to eight debug value registers DVR0 through DVR7, up to eight debug control registers DCR0 through DCR7, and two debug watchpoint counter registers DWCR0 and DWCR1. Each register is implemented only when its corresponding macro is enabled; otherwise it is represented by a constant zero-valued wire or is absent from the read path. The register select signals are decoded from spr_cs and spr_addr[10:0]. Implemented registers are written on the rising edge of clk when their select signal is active and spr_write is asserted, and are reset asynchronously on rst.

The SPR read path is conditionally implemented under OR1200_DU_READREGS. When enabled, spr_dat_o returns the selected debug register contents based on spr_addr[10:0]. Implemented DVRs return 32-bit compare values, implemented DCRs return their 8-bit control fields zero-extended to 32 bits, DMR1 and DMR2 return their debug-mode contents zero-extended to 32 bits, DWCR0 and DWCR1 return their full 32-bit counter registers, and DSR/DRR return their 14-bit contents zero-extended to 32 bits. If trace-buffer support is enabled, trace-buffer address and data registers are also readable through this path. Unmatched addresses return zero.

The DSR register is exposed through du_dsr, which is simply assigned from the internal dsr register. The du_except input is already described in the source as an exception vector masked by DSR. Inside this module, du_except is decoded into the 14-bit except_stop vector. This decoded vector is used to indicate exception-related breakpoint conditions and to update the debug reason register. The module itself does not directly use DSR to mask exceptions internally; instead, it stores DSR and exports it through du_dsr for use by surrounding exception/debug control logic.

The DRR register records exception-stop reasons. On reset it is cleared to zero. When the DRR SPR address is written, it is loaded from spr_dat_i[13:0]. Otherwise, on each clock cycle, it accumulates exception-stop information by OR-ing its current value with except_stop. Therefore, in this implementation, DRR mainly records decoded exception-stop bits from du_except; it is not a complete record of every possible debug event such as all watchpoint, branch-trace, or single-step events.

The external breakpoint output dbg_bp_o is registered as dbg_bp_r. On reset it is cleared. When the execute stage is not frozen, it is set according to the decoded exception-stop vector and, depending on enabled macros, single-step and branch-trace conditions controlled by DMR1. Specifically, exception stops assert it whenever any bit of except_stop is set. If single-step support is enabled, non-NOP execute-stage instructions can assert it when the corresponding DMR1 bit is set. If branch-trace support is enabled, a non-NOP branch operation can assert it when the corresponding DMR1 bit is set. When the execute stage is frozen, the registered breakpoint output follows only the exception-stop condition.

When hardware watchpoint support is enabled with OR1200_DU_HWBKPTS, the module implements eight programmable compare conditions. Each compare condition is controlled by one DCR/DVR pair. The DCR field dcrN[7:5] selects what value is compared, such as instruction fetch effective address id_pc, load address, store address, load data, store data, load/store address, or load/store data selected according to dcpu_we_i. The comparison strobe is disabled when the compare type is zero, always active for instruction-fetch address comparison, and driven by dcpu_cycstb_i for data load/store-related comparisons.

For each watchpoint compare condition, the DCR comparison field selects the comparison relation against the corresponding DVR value. Supported relations include equality, less-than, less-than-or-equal, greater-than, greater-than-or-equal, and inequality. The comparison uses the selected compare target and the associated debug value register. The DCR sign-control bit participates in the comparison by modifying the most significant bit before comparison.

The individual match results match0 through match7 are combined into internal watchpoint bits wp[0] through wp[7] according to fields in DMR1. For watchpoint 0, the result is normally the direct match result unless disabled. For watchpoints 1 through 7, each DMR1 control field can make the corresponding watchpoint bit equal to the direct match result, the logical AND of the direct match with the previous watchpoint bit, the logical OR of the direct match with the previous watchpoint bit, or zero when disabled. This allows chained watchpoint expressions to be formed from multiple compare conditions.

The module also supports two watchpoint counters when DWCR0 and DWCR1 are implemented. Each counter register contains a count field and a compare/match value field. The lower 16-bit count field increments when the corresponding DMR2 enable bit is set and selected internal watchpoint events occur. A counter-match condition is generated when the configured upper 16-bit value equals the lower 16-bit count. These counter matches are then used as additional internal watchpoint bits. In addition, the external watchpoint trigger input dbg_ewt_i is used as another internal watchpoint source.

The hardware breakpoint request output du_hwbkpt is generated only from the internal watchpoint vector and the corresponding enable/mask bits in DMR2. When hardware watchpoints are enabled, du_hwbkpt is asserted if any enabled internal watchpoint bit is active. It is not a combined output for all debug stop reasons. Exception-stop, single-step, and branch-trace conditions primarily affect dbg_bp_o, while du_hwbkpt represents enabled hardware watchpoint-triggered trap requests. If hardware watchpoint support is not enabled, du_hwbkpt is assigned zero.

If trace-buffer support is enabled with OR1200_DU_TB_IMPLEMENTED, the module also implements a simple trace buffer. The trace buffer records execution-related information when the execute stage is not frozen and the executed instruction is not the special NOP form excluded by the source logic. It maintains an 8-bit write address and a timestamp counter. The trace buffer stores recent values of the next program counter spr_dat_npc, execute-stage instruction ex_insn, register-file/ALU writeback data rf_dataw, and timestamp tb_timstmp into separate 256-entry RAMs. These trace-buffer contents can be read through the SPR read path using the trace-buffer SPR addresses. If trace-buffer support is not enabled, the trace-buffer read-data outputs are fixed to zero.

When OR1200_DU_IMPLEMENTED is not enabled, the module degenerates into a minimal debug-access bridge. The direct debug interface forwarding still remains: external debug accesses still drive du_addr, du_dat_o, du_read, du_write, and dbg_dat_o, and dbg_ack_o still acknowledges dbg_stb_i with a one-cycle delay. However, the debug-register and breakpoint logic is disabled: dbg_bp_o is fixed to zero, du_dsr is fixed to zero, du_hwbkpt is fixed to zero, and, when debug-register reads are compiled in, spr_dat_o is fixed to zero.

In summary, or1200_du is both a debug access bridge and a configurable debug-event unit. It forwards external debugger accesses to the CPU-internal debug interface, stores and exposes debug configuration/status registers through SPRs, decodes exception-stop inputs, generates registered breakpoint indications, optionally performs programmable hardware watchpoint comparisons and counter-based watchpoint triggering, and optionally records execution trace information. CPU stalling is controlled directly by the external dbg_stall_i signal; internal debug events do not directly drive du_stall. The internal watchpoint logic can generate du_hwbkpt, but the external dbg_wp_o port is fixed to zero in this implementation.

Processing Flow

The module operates through several functional paths that work in parallel and are controlled by compile-time configuration macros.

First, the external debug interface is forwarded to the CPU-internal debug access interface. The external address, write data, strobe, and write-enable signals are converted into internal debug address, write data, read-enable, and write-enable signals. Read data from the CPU-internal debug path is returned directly to the external debugger. The external acknowledge signal is generated by registering the external strobe signal for one clock cycle.

Second, CPU stall control is handled directly by the external debugger. The internal stall request output is assigned directly from the external stall input. Internal debug events such as decoded exceptions, single-step conditions, branch-trace conditions, and watchpoint matches do not directly assert the stall output.

Third, when the debug unit is implemented, the SPR interface selects and accesses the debug registers. Register select signals are decoded from the SPR chip-select signal and the lower SPR address bits. Implemented registers are reset asynchronously, updated on the rising clock edge during valid SPR writes, and optionally read back through the SPR read-data output when debug-register read support is enabled.

Fourth, the exception-stop path decodes the `du_except` input into an internal `except_stop` vector. The source describes `du_except` as already masked by DSR. This module stores the DSR register and forwards it through `du_dsr`, while the decoded `except_stop` vector is used internally for breakpoint indication and debug-reason recording.

Fifth, the debug reason register records exception-stop causes. DRR is cleared on reset, can be explicitly written through the SPR interface, and otherwise accumulates decoded exception-stop bits by OR-ing in `except_stop`. It does not record every debug event generated by the module.

Sixth, the breakpoint indication path generates the registered external breakpoint output. The breakpoint output is asserted for decoded exception-stop conditions and, when the corresponding compile-time options are enabled, may also be asserted by single-step and branch-trace conditions controlled by DMR1.

Seventh, if hardware watchpoints are implemented, each DCR/DVR pair forms one programmable compare condition. The DCR selects the comparison target, comparison timing, comparison type, and sign-control behavior, while the DVR provides the compare value. The resulting match signals are combined through DMR1-controlled chaining logic to produce internal watchpoint bits.

Eighth, optional watchpoint-counter logic extends the internal watchpoint vector. The DWCR counters increment on selected watchpoint events and generate counter-match watchpoint conditions when their configured compare fields equal their count fields. The external watchpoint trigger input also contributes to the internal watchpoint vector.

Ninth, the hardware breakpoint request output is generated from the internal watchpoint vector masked by the corresponding DMR2 enable bits. This output represents enabled hardware-watchpoint trap requests only; it is not a combined debug-stop output for all exception, single-step, branch-trace, and watchpoint causes.

Tenth, if trace-buffer support is implemented, the module records execution trace information when the execute stage is not frozen and the current instruction is not the excluded NOP form. It stores recent next-PC, instruction, register-file/writeback result, and timestamp values into trace-buffer RAMs, which are readable through the SPR interface.

Finally, if the full debug unit is not implemented, the module retains only the basic external debug access forwarding and acknowledge generation. Debug registers, exception/breakpoint logic, hardware watchpoint logic, and trace-buffer logic are disabled or tied to zero according to the compile-time configuration.
