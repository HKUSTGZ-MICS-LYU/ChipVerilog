or1200_immu_top is the instruction-side MMU top-level module of the OR1200 processor. It is located between the CPU instruction-fetch interface and the downstream instruction memory / QMEM interface. On the instruction-fetch path, it performs ITLB lookup, virtual-to-physical address translation, TLB miss detection, execute-permission fault detection, ITLB SPR access control, and downstream fetch-request gating. The CPU provides the instruction virtual address and fetch request to this module. When the required conditions are satisfied, the module outputs an address and access request to the downstream side. If an ITLB miss, permission fault, or downstream error occurs, the module reports the exception or error through CPU-side status signals.

The module uses clk as the main clock and uses the asynchronous active-high reset rst to initialize internal state. The CPU-side address output icpu_adr_o is a registered copy of the input address icpu_adr_i. After reset, it is initialized to 32'h0000_0100, and then updates to the current input address on clock edges. It should be noted that icpu_adr_o is the registered address output on the CPU-side interface, not the translated address sent to the downstream memory system. The downstream access address is provided by qmemimmu_adr_o.

On the CPU instruction-side interface, icpu_adr_i represents the instruction virtual address issued by the CPU, and icpu_cycstb_i represents the current fetch request. immu_en is the runtime IMMU enable signal, which controls whether ITLB lookup and translation-related request gating are enabled. supv indicates whether the processor is currently in supervisor mode, and it is used to select the execute-permission check. A user-mode fetch requires the user execute permission in the ITLB entry, while a supervisor-mode fetch requires the supervisor execute permission. ic_en is an instruction-cache-enable-related input, but it does not participate in the effective control logic of this module.

The module returns access status to the CPU through icpu_tag_o, icpu_rty_o, and icpu_err_o. icpu_tag_o indicates the returned tag, with the priority order of TLB miss over page fault over downstream tag. In other words, when a TLB miss occurs, the module returns the TLB miss tag; when a permission fault occurs, it returns the page fault tag; otherwise, it passes through the downstream tag. icpu_err_o is asserted when a TLB miss, permission fault, or downstream error occurs. icpu_rty_o indicates a retry / wait state to the CPU. It can come either from the downstream interface or from the local wait condition during an ITLB SPR access.

The SPR interface is used to access the special-purpose registers associated with the ITLB. spr_cs indicates SPR access selection, spr_write indicates a write access, spr_addr is the SPR address, spr_dat_i is the write data, and spr_dat_o is the read data. When there is a valid SPR access, spr_dat_o returns the read data from the ITLB; otherwise, it returns zero. The SPR access request actually sent to the ITLB is controlled by dis_spr_access, in order to avoid conflicts between consecutive SPR accesses and the normal instruction translation flow. dis_spr_access is cleared on reset, cleared when the CPU-side retry is released, and set while the SPR access continues, thereby controlling the valid window of the ITLB SPR access.

The module internally stores the virtual page number from the previous cycle in icpu_vpn_r. This register latches the virtual page number portion of the current input address every cycle. page_cross is generated by comparing the current virtual page number with the virtual page number saved from the previous cycle. Therefore, it indicates that the current VPN differs from the previous-cycle VPN. This signal is used to prevent the module from incorrectly using the previous-cycle address or ITLB lookup result to issue a downstream access when the page number changes.

In a normal IMMU build, an ITLB lookup is triggered jointly by the runtime immu_en signal and the CPU fetch request. itlb_en indicates whether an ITLB lookup is issued in the current cycle. itlb_en_r is its one-cycle delayed version, and it is suppressed during an ITLB SPR access. itlb_done indicates that the ITLB lookup issued in the previous cycle can be used in the current cycle for address formation and exception judgment, while also requiring that no VPN change is detected in the current cycle. Therefore, itlb_done is the key condition used by this module to determine whether the ITLB lookup result is usable.

TLB miss detection is performed only when itlb_done is asserted. When the ITLB lookup result is valid but does not hit, the module generates a TLB miss. Permission fault detection is also performed only when itlb_done is asserted. For a user-mode fetch, a fault is generated if the ITLB entry does not allow user execution. For a supervisor-mode fetch, a fault is generated if the ITLB entry does not allow supervisor execution. Both miss and fault assert the CPU-side error signal and affect the CPU-side tag output.

The downstream request signal qmemimmu_cycstb_o is generated in two different ways depending on the runtime value of immu_en. When immu_en is asserted, the module issues a downstream access only if the CPU has a fetch request, the ITLB lookup has completed, no TLB miss has occurred, no permission fault has occurred, and no page crossing is detected. When immu_en is deasserted, the module does not require ITLB lookup completion and forwards the CPU fetch request as long as there is no page crossing. Runtime deassertion of immu_en only means that ITLB lookup and translation gating are not enabled; it is not equivalent to a compile-time build with the IMMU completely removed.

In a normal IMMU build, the downstream address qmemimmu_adr_o is determined by itlb_done. When itlb_done is asserted, the module forms the downstream access address by concatenating the physical page number returned by the ITLB with the current page offset. When itlb_done is deasserted, the module concatenates the virtual page number saved from the previous cycle with the current page offset. In other words, in a normal IMMU build, the address-selection condition is ITLB lookup completion, not immu_en directly. Therefore, when immu_en is disabled at runtime, the downstream request can be forwarded in a relatively transparent way, but the address output still follows this address-selection mechanism and is not exactly a bit-by-bit pass-through of the input address.

The downstream cache-inhibit output qmemimmu_ci_o is fixed to the architecturally defined IMMU cache-inhibit constant. Although the ITLB returns a cache-inhibit attribute bit, this top-level module does not propagate that attribute to the downstream interface. Therefore, the downstream cache-inhibit behavior of this module is fixed rather than dynamically determined by the ITLB entry.

In a normal IMMU build, the module instantiates the instruction-side ITLB. The ITLB receives the lookup enable signal and the current virtual address, and returns the hit status, physical page number, user-mode execute permission, supervisor-mode execute permission, and cache-inhibit attribute. The hit status is used to detect TLB misses, the physical page number is used to form the downstream address, and the execute permissions are used for fault detection. The cache-inhibit attribute does not participate in downstream output control at this top level. The ITLB also supports software reads and writes of its internal entries through the SPR interface, and it can connect to test-related signals when the BIST configuration is enabled.

When a build configuration with the IMMU completely removed is used, the module does not perform ITLB lookup, address translation, TLB miss detection, or permission fault detection. Instead, it degenerates into a basic pass-through path. In this mode, the downstream address comes directly from the CPU input address, the downstream tag, retry, and error signals are returned directly to the CPU, the SPR read data is fixed to zero, and the cache-inhibit output remains at the architecturally defined constant. If the BIST-related configuration is enabled, the test chain is also connected in bypass form.

Overall, when or1200_immu_top is built with normal IMMU support and runtime immu_en is asserted, it performs a one-cycle delayed ITLB lookup for the instruction virtual address issued by the CPU, forms the downstream access address according to the lookup result, and issues a downstream fetch request when the lookup hits and the required permission is present. If the ITLB does not hit or the current execution mode lacks the corresponding execute permission, the module blocks the downstream request and reports the exception through the CPU-side error and tag signals. If immu_en is disabled at runtime, the module forwards fetch requests when there is no VPN change, but the address output still follows the address-selection mechanism of the normal IMMU branch. If the module is built without IMMU support, it degenerates into a pass-through path with no address translation and no local MMU exception detection.

    // Rst and clk
    input clk,
    input rst,

    // CPU i/f
    input ic_en,
    input immu_en,
    input supv,
    input [31:0] icpu_adr_i,

    output [31:0] icpu_adr_o,
    output [3:0] icpu_tag_o,
    output icpu_rty_o,
    output icpu_err_o,

    // SPR access
    input spr_cs,
    input spr_write,
    input [31:0] spr_addr,

`ifdef OR1200_BIST

    input mbist_si_i,
    output mbist_so_o,

    // QMEM i/f
    input qmemimmu_rty_i,
    input qmemimmu_err_i,
    input [3:0] qmemimmu_tag_i,
    output [31:0] qmemimmu_adr_o,
    output qmemimmu_cycstb_o,
    output qmemimmu_ci_o
);

Processing Flow

In a normal IMMU build with runtime immu_en asserted, the module processes an instruction fetch request in a delayed translation flow. First, the CPU presents an instruction virtual address on icpu_adr_i and asserts icpu_cycstb_i to request an instruction fetch. The module enables an ITLB lookup using the current virtual address, while also registering the current virtual page number for alignment with the delayed lookup result.

On the following cycle, the module determines whether the previous ITLB lookup result can be used. This is indicated by itlb_done, which requires that a valid lookup was issued in the previous cycle and that the current virtual page number has not changed relative to the registered page number. If a page change is detected, the module prevents the potentially mismatched translation result from being used for a downstream request.

When the ITLB result is usable, the module checks whether the lookup hit. If the lookup misses, it raises a TLB miss condition, blocks the downstream fetch request, asserts the CPU-side error output, and returns the TLB miss tag. If the lookup hits, the module then checks execute permission according to the current privilege mode. A user-mode fetch requires user execute permission, while a supervisor-mode fetch requires supervisor execute permission. If the required permission is missing, the module raises a page fault, blocks the downstream request, asserts the CPU-side error output, and returns the page fault tag.

If the ITLB lookup hits and the required execute permission is present, the module forms the downstream address by concatenating the physical page number returned by the ITLB with the current page offset. It then asserts the downstream request signal when the CPU fetch request is still active and no page crossing, TLB miss, or page fault is present. Downstream retry, error, and tag responses are then propagated back to the CPU unless overridden by a local MMU exception.

When runtime immu_en is deasserted in a normal IMMU build, the module does not require a completed ITLB lookup before forwarding the request. It forwards the CPU fetch request as long as no page crossing is detected, but the downstream address still follows the normal address-selection mechanism controlled by itlb_done. This behavior should be distinguished from a build configuration in which the IMMU is completely removed.

During ITLB SPR accesses, the module temporarily gives priority to the SPR access path over the normal translation flow. The SPR access is gated by the internal dis_spr_access control, and the CPU-side retry output is asserted while the ITLB SPR access is active. This prevents normal instruction fetch progression from conflicting with software access to the ITLB entries.

In a build configuration without IMMU support, the processing flow is simplified. The module does not issue ITLB lookups, does not perform translation or permission checks, and does not generate local TLB miss or page fault conditions. Instead, it forwards the CPU address and request to the downstream side and returns the downstream response signals directly to the CPU.
