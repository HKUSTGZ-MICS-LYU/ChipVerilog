The or1200_sprs module is responsible for access decoding, read/write control, and system-group register control signal generation for the OR1200 processor’s SPRs, or Special Purpose Registers. It sits between the CPU execution path, the Debug Unit, and the individual SPR functional blocks. Its role is to convert both ordinary CPU-side l.mtspr/l.mfspr operations and Debug Unit internal accesses into a unified SPR address, group chip-select, write enable, write data, and readback data path. The only major state register stored locally in this module is sr; registers such as EPCR, EEAR, ESR, NPC, and PPC are stored externally and provided to this module as inputs. This module is responsible for decoding access to them, multiplexing their read data, and generating their write-enable signals.

The module first arbitrates between ordinary CPU accesses and Debug Unit accesses. du_access is generated as du_read | du_write. Whenever the Debug Unit initiates a read or write access, the Debug Unit path takes priority. When du_write is asserted, sprs_op is forced to OR1200_ALUOP_MTSR; when du_read is asserted, sprs_op is forced to OR1200_ALUOP_MFSR; otherwise, sprs_op uses the alu_op value from the execution unit. Therefore, Debug Unit access is not implemented as a completely separate decode path. Instead, it is mapped onto ordinary SPR read/write operations and reuses the subsequent SPR decoding logic.

The SPR address spr_addr is also generated with Debug Unit priority. When du_access is asserted, spr_addr is taken directly from du_addr. Otherwise, for ordinary CPU access, the SPR address is formed by bitwise OR-ing addrbase with the zero-extended addrofs, namely addrbase | {16'h0000, addrofs}. This is not additive addressing, so it should not be described as adding the offset to the base. The SPR write-data output spr_dat_o takes du_dat_du during a Debug Unit write access; otherwise, it takes the ordinary data-path input dat_i. This signal represents the write data sent to the target SPR unit, not readback data from the SPR bus.

The Debug Unit return data du_dat_cpu selects different sources depending on the access type. When du_write is asserted, du_dat_cpu echoes du_dat_du; when du_read is asserted, it returns the SPR read-data path to_wbmux; otherwise, it outputs dat_i. Thus, when the Debug Unit reads an SPR, it observes the same to_wbmux value selected by the ordinary SPR group read-data path, rather than using a separate Debug Unit-specific read channel.

The SPR write enable spr_we is generated as du_write | write_spr, where write_spr comes from the combinational decode of sprs_op as an MTSR operation. The SPR group chip-select spr_cs is produced by AND-ing the one-hot decode result unqualified_cs, derived from spr_addr[15:11], with {32{read_spr | write_spr}}. In other words, unqualified_cs only indicates which one of the 32 SPR groups is addressed, while the final spr_cs output is asserted only when the current operation is actually an SPR read or write. This signal is a group chip-select output for all SPR groups, not a chip-select used only internally by this module.

Within the system SPR group, the module further decodes the address to generate specific register-select signals, including cfgr_sel, rf_sel, npc_sel, ppc_sel, sr_sel, epcr_sel, eear_sel, and esr_sel. All of these select signals depend on spr_cs[0], so they can only be asserted when SPR group 0, the system group, is selected. cfgr_sel and rf_sel use coarser-grained address matching and correspond to the configuration-register region and the register-file access window, respectively. npc_sel, ppc_sel, sr_sel, epcr_sel, eear_sel, and esr_sel use full system SPR address matching.

The system-group write enables are generated by combining these select signals with write_spr. pc_we is asserted when NPC or PPC is written. epcr_we, eear_we, and esr_we are asserted when EPCR, EEAR, and ESR are written, respectively. sr_we is asserted when SR is written, when RFE is executed, when the ALU updates the flag bit, or when the ALU updates the carry bit. It is important to note that sr_we only controls whether SR is updated with to_sr in non-exception-entry cases. Exception entry through except_started has higher priority and does not depend on sr_we.

to_sr is the combinationally generated next value for SR, but it does not include the handling of except_started. For to_sr[15:11], an RFE operation has highest priority and restores esr[15:11]. During an ordinary MTSR write to SR, bit 15 is forced to 1'b1, while bits 14 through 11 come from spr_dat_o[14:11]; otherwise, the current sr[15:11] value is preserved. For the carry bit to_sr[10], the priority order is RFE restoring esr[10], cy_we writing cyforw, MTSR writing spr_dat_o[10], and then preserving the old value. For the flag bit to_sr[9], the priority order is RFE restoring esr[9], flag_we writing flagforw, MTSR writing spr_dat_o[9], and then preserving the old value. For to_sr[8:0], RFE first restores esr[8:0]; otherwise, an MTSR write supplies spr_dat_o[8:0]; if neither applies, the old value is kept.

The SR register sr is sequential state stored inside this module and is updated on the rising edge of clk or the rising edge of rst. On reset, sr is initialized to the architecture-defined default value, including the initial supervisor-mode setting and the default exception-prefix configuration. After reset, if except_started is asserted, indicating that exception entry has started, the module directly modifies several SR control bits: it sets sr[0] to 1 and clears sr[1], sr[2], sr[5], and sr[6]. This exception-entry update has priority over ordinary sr_we updates. Only when exception entry is not active and sr_we is asserted is sr updated as a whole with to_sr[15:0].

The SPR read-data path is implemented by to_wbmux. When sprs_op is MTSR, write_spr is asserted, read_spr is deasserted, and to_wbmux outputs zero. When sprs_op is MFSR, read_spr is asserted and write_spr is deasserted. In that case, the module selects the read-data source according to spr_addr[15:11]: the tick timer group returns spr_dat_tt, the PIC group returns spr_dat_pic, the power management group returns spr_dat_pm, the DMMU group returns spr_dat_dmmu, the IMMU group returns spr_dat_immu, the MAC group returns spr_dat_mac, the Debug Unit group returns spr_dat_du, and the system group returns sys_data. For all other ALU operations, both SPR read and write are disabled, and to_wbmux outputs zero.

sys_data is the read-data multiplexing result for the system group. It uses multiple 32-bit masks, generated from read_spr and the specific register-select signals, to AND-mask and OR-combine spr_dat_cfgr, spr_dat_rf, spr_dat_npc, spr_dat_ppc, the zero-extended sr, epcr, eear, and the zero-extended esr. Since these select signals are produced by mutually exclusive address decoding, the final sys_data corresponds to the currently addressed system SPR register.

The module also exports selected SR bits as independent status outputs. flag is directly connected to sr[9], and carry is directly connected to sr[10]. Therefore, after the ALU updates the flag and carry bits through flag_we/flagforw and cy_we/cyforw, these two outputs reflect the corresponding state currently stored in SR.

Overall, or1200_sprs can be understood as the SPR access crossbar and system-SPR control center inside the OR1200 processor. It unifies ordinary l.mtspr/l.mfspr instruction accesses and Debug Unit accesses, performs SPR group decoding, performs system-group internal register decoding, generates write-enable signals, forwards write data, and multiplexes read data. At the same time, it locally maintains SR and controls the priority among RFE, ALU flag/carry updates, ordinary MTSR writes to SR, and SR bit updates during exception entry. Exception-entry partial modification of SR has the highest priority; RFE and ordinary SR writes are implemented through the to_sr combinational path; and Debug Unit accesses take priority over the ordinary address and write-data paths while reusing the standard SPR access mechanism.

Processing Flow

The module processes an SPR access through the following logical flow. First, it determines whether the access comes from the Debug Unit or from the ordinary CPU execution path. If du_read or du_write is asserted, the Debug Unit path takes priority: du_addr is used as the SPR address, du_write is treated as an MTSR operation, and du_read is treated as an MFSR operation. If no Debug Unit access is active, the module uses the CPU-side alu_op and forms the SPR address from addrbase | {16'h0000, addrofs}.

Next, the module decodes the effective SPR operation. An MTSR operation asserts write_spr, deasserts read_spr, drives the SPR write-data path through spr_dat_o, and causes spr_we to be asserted. An MFSR operation asserts read_spr, deasserts write_spr, and selects the appropriate read-data source into to_wbmux. Other ALU operations disable both SPR read and write behavior.

After the operation type is known, the module decodes spr_addr[15:11] into a one-hot SPR group select. This raw group select is then qualified by read_spr | write_spr to produce spr_cs, ensuring that no SPR group is selected unless the current operation is an actual SPR read or write. If the selected group is the system group, the module further decodes the lower address bits to identify CFGR, RF, NPC, PPC, SR, EPCR, EEAR, or ESR.

For writes to the system group, the module generates register-specific write enables. Writes to NPC or PPC assert pc_we; writes to EPCR, EEAR, or ESR assert epcr_we, eear_we, or esr_we; writes to SR participate in the SR update path through sr_we. The SR update path also accepts RFE, flag updates, and carry updates. However, exception entry through except_started has higher priority than the ordinary sr_we path and directly modifies selected SR control bits.

For reads, the module selects a group-level data source according to spr_addr[15:11]. Non-system groups return data from their corresponding external SPR blocks, such as TT, PIC, PM, DMMU, IMMU, MAC, or DU. If the system group is selected, sys_data is generated by masking and OR-combining the selected system-register read source. The final read value is driven to to_wbmux, and during a Debug Unit read it is also returned through du_dat_cpu.
