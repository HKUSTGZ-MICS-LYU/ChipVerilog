or1200_reg2mem is a combinational store write-data alignment module used in the OR1200 LSU. It converts the 32-bit register-side write data regdata into the 32-bit memory-bus-side write data memdata, so that the byte or halfword to be written appears on the memory byte lane corresponding to the target address offset. This module does not generate byte-enable signals and does not check whether the memory access is valid. It assumes that the upstream LSU has already generated the correct byte select signal, such as dcpu_sel_o, based on lsu_op and addr[1:0].

The input addr[1:0] indicates the byte offset of the target store address within a 32-bit word. The input lsu_op[3:0] is the LSU operation code. The input regdata[31:0] is the register-side data to be stored. The output memdata[31:0] is the write-data word after rearrangement according to the memory-bus byte lanes, and it is intended to be used together with the byte-enable signal generated by the LSU. For this module, the store operation codes SB, SH, and SW affect the data arrangement; other operation codes fall through to the default branches of the individual multiplexers.

The module is implemented entirely as combinational logic and has no clock, reset, or saved state. Although the internal signals memdata_hh, memdata_hl, memdata_lh, and memdata_ll are declared as Verilog reg types, they are only temporary variables assigned inside combinational always blocks and do not represent sequential registers. The final output memdata is formed by concatenating these four 8-bit variables. memdata_hh corresponds to memdata[31:24], memdata_hl corresponds to memdata[23:16], memdata_lh corresponds to memdata[15:8], and memdata_ll corresponds to memdata[7:0].

For the highest byte, memdata[31:24], the module selects the input data according to lsu_op and addr[1:0]. When a byte store SB is performed with address offset 2'b00, this byte is assigned regdata[7:0], placing the low 8 bits of the store data onto the highest byte lane. When a halfword store SH is performed with address offset 2'b00, this byte is assigned regdata[15:8], which is the upper byte of the halfword data. In all other cases, memdata[31:24] defaults to regdata[31:24].

For memdata[23:16], the byte is assigned regdata[23:16] only when a word store SW is performed with address offset 2'b00, preserving the original byte position for an aligned word store. In all other cases, memdata[23:16] defaults to regdata[7:0]. Therefore, for a byte store to address offset 2'b01, this lane carries the low 8 bits of the store data that are actually intended to be written. In other cases, if this lane is not selected by the byte select signal, its value will not actually be written to memory.

For memdata[15:8], when a byte store SB is performed with address offset 2'b10, this byte is assigned regdata[7:0], placing the low 8 bits of the store data onto the corresponding byte lane. In all other cases, memdata[15:8] defaults to regdata[15:8]. This allows the byte to preserve the corresponding middle byte of the register data for aligned word stores or for store cases where that byte is selected by the LSU byte-enable logic.

The lowest byte, memdata[7:0], is not controlled by lsu_op or addr[1:0]; it is always assigned directly from regdata[7:0]. Therefore, it depends only on the low 8 bits of regdata. When a byte store targets the lowest byte lane, or when a halfword or word store requires the lowest byte, this position already contains the correct data.

It is important to note that this module does not guarantee that all four byte lanes of memdata contain semantically meaningful data for every store type. For byte stores and halfword stores, only the lanes selected by the LSU byte-enable signal are actually written to memory; the unselected lanes may simply contain default copies of certain bytes from regdata. The key responsibility of this module is to ensure that each selected byte lane carries the correct store data: regdata[7:0] for byte stores, or the corresponding byte from regdata[15:0] for halfword stores.

The selection logic in the code uses casex({lsu_op, addr[1:0]}). Under normal operating conditions, lsu_op and addr[1:0] are expected to have known values. If these signals contain x or z values during simulation, casex may treat them as don't-care bits during matching. Therefore, the intended behavior of this module should be understood as store write-data byte-lane alignment under valid and known LSU operation-code and address-offset inputs.

module or1200_reg2mem(
    input [1:0] addr,
    input [3:0] lsu_op,
    input [31:0] regdata,
    output [31:0] memdata
);

Input ports:
    - addr[1:0]: Byte offset of the target store address within a word.
    - lsu_op[3:0]: Encoded load/store operation selector.
    - regdata[31:0]: Register-side aligned data word.
Output port:
    - memdata[31:0]: Memory-side data word before alignment or extension.
Internal reg/wire signals:
    reg [7:0] memdata_hh: Memory-data [31:24] byte.
    reg [7:0] memdata_hl: Memory-data [23:16] byte.
    reg [7:0] memdata_lh: Memory-data [15:8] byte.
    reg [7:0] memdata_ll: Memory-data [7:0] byte.

Processing Flow

When any relevant input changes, the module combinationally evaluates the byte-lane selection logic for memdata. The LSU operation code lsu_op and the address offset addr[1:0] determine which bytes of regdata are placed onto the corresponding memory byte lanes. Each byte of memdata is generated independently by a small multiplexer, and the four generated bytes are then concatenated to form the final 32-bit memory-side write-data word.

For store byte operations, the low byte regdata[7:0] is placed onto the byte lane selected by the address offset. For store halfword operations, the low halfword regdata[15:0] is placed onto the selected halfword-aligned byte lanes. For store word operations, the register data is preserved in the normal aligned word layout. Bytes that are not selected by the LSU byte-enable signal may contain default values from regdata, but they are not intended to be written to memory.

The resulting memdata is used together with the LSU-generated byte select signal, such as dcpu_sel_o, to perform the actual store on the memory interface. The module itself does not latch data, generate byte enables, or validate address alignment; it only performs the register-side to memory-side byte-lane data arrangement.
