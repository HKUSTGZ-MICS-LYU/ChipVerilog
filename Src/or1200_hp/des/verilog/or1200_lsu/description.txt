or1200_lsu is the front-end load/store unit module in the OR1200 processor memory-access path. It generates the data access address from the base address addrbase and offset addrofs, and produces the data-side access request, write enable, byte-select signal, and access tag according to the LSU operation type lsu_op. The module also checks address alignment for halfword and word accesses, and classifies exception types according to the error signal and tag returned from the data side. Byte-position adjustment, sign extension, zero extension, and other data-format conversion functions for load and store data are handled by the two submodules or1200_mem2reg and or1200_reg2mem.

This module does not contain an independent request state machine, nor does it contain sequential registers for storing memory transaction state. Its LSU-level control signals are mainly generated by combinational logic, while read/write data-format conversion is performed by the instantiated alignment submodules. Therefore, this module is more accurately described as a combinational control and data-format conversion module between the LSU and the data cache or data memory interface, rather than a complete standalone memory transaction controller.

In the internal interface, addrbase is the memory-access base address input, and addrofs is the memory-access offset input. The two are added together to form the final data access address. lsu_op is the LSU operation-type encoding, used to distinguish different load/store types, such as byte, halfword, and word accesses, as well as signed or unsigned loads. lsu_datain is the store data from the register side. It is sent to or1200_reg2mem, where it is adjusted to the correct data-bus byte position according to the low two bits of the access address and the operation type. lsu_dataout is the load data returned to the register side. It is generated by or1200_mem2reg according to the data-side returned value, the low two bits of the address, and the operation type.

lsu_stall is the LSU stall indication signal. It is asserted when this module is issuing an access request to the data side and the data side returns dcpu_rty_i. lsu_unstall is the LSU unstalled indication signal, and is directly equal to the data-side dcpu_ack_i. It should be noted that lsu_unstall only indicates that an acknowledge has been received from the data side; it does not distinguish whether the access completed normally or returned with an exception. If an error is returned, the error type is indicated separately by except_dtlbmiss, except_dmmufault, and except_dbuserr. du_stall is the debug-unit stall input. When this signal is asserted, the LSU does not issue a new access request to the data side.

In the data-side interface, dcpu_adr_o is the access address output to the data cache or data memory side, and its value is always equal to addrbase + addrofs. This address is used not only as the external access address, but also internally for address alignment checking, byte-select signal generation, and low-address-bit selection for the read/write data alignment submodules. In the code, dcpu_adr_o[1:0] is extracted as mem2reg_addr. Although this signal is named mem2reg_addr, it is connected to both or1200_mem2reg and or1200_reg2mem, and is used for data-position adjustment in both the load and store directions.

The data-side request signal dcpu_cycstb_o is asserted only when lsu_op is nonzero and no blocking condition is active. Specifically, when any of du_stall, lsu_unstall, or except_align is 1, dcpu_cycstb_o is forced to 0; otherwise, it is equal to |lsu_op. Here, du_stall indicates that the debug unit requests a stall, lsu_unstall indicates that an acknowledge has been received from the data side in the current cycle, and except_align indicates that the current access has an address alignment exception. These three conditions are equivalent combinational gating conditions, not state-machine priorities with an ordering. As long as any one of them is asserted, this module does not issue an access request to the data side.

The write-enable signal dcpu_we_o is directly determined by lsu_op[3]. Therefore, this module assumes that the most significant bit of the LSU operation encoding is used to distinguish stores from loads. The exact encodings for load and store operations are defined by the macros in or1200_defines.v. The access tag dcpu_tag_o is generated according to whether the request is valid: when dcpu_cycstb_o is asserted, it outputs the normal data access tag OR1200_DTAG_ND; when there is no valid request, it outputs the idle tag OR1200_DTAG_IDLE. The tag output by this module only indicates whether the current operation is a normal data access. Exception types returned by the downstream data side are determined by combining dcpu_err_i and dcpu_tag_i.

The address alignment exception except_align is generated combinationally. For halfword accesses, including SH, LHZ, and LHS, the least significant bit of the access address, dcpu_adr_o[0], must be 0. If this bit is 1, an alignment exception is generated. For word accesses, including SW, LWZ, and LWS, the low two bits of the access address, dcpu_adr_o[1:0], must be 2'b00. If either of the low two bits is 1, an alignment exception is generated. Byte accesses do not require alignment checking, so SB, LBZ, and LBS do not generate except_align due to different low address bits. When except_align is asserted, dcpu_cycstb_o is forced to 0, so misaligned halfword or word accesses are not sent to the data side.

Data-side error exceptions are generated by combinational decoding of dcpu_err_i and dcpu_tag_i. When dcpu_err_i is asserted and dcpu_tag_i is equal to OR1200_DTAG_TE, the module asserts except_dtlbmiss, indicating a data TLB miss. When dcpu_err_i is asserted and dcpu_tag_i is equal to OR1200_DTAG_PE, the module asserts except_dmmufault, indicating a data MMU permission or protection fault. When dcpu_err_i is asserted and dcpu_tag_i is equal to OR1200_DTAG_BE, the module asserts except_dbuserr, indicating a data bus error. These exception signals are only combinational classifications of downstream data-side error responses. The module itself does not store exception state, delay exceptions, or arbitrate among them sequentially.

lsu_stall and lsu_unstall are used together with the pipeline stall control logic. lsu_stall is equal to dcpu_rty_i & dcpu_cycstb_o, so it is asserted only when the LSU is currently issuing a request to the data side and the data side returns a retry or wait signal. This signal indicates that the current data access has not yet been accepted or completed by the data side, so the pipeline needs to remain stalled. lsu_unstall is directly equal to dcpu_ack_i, indicating that the data side has acknowledged the access and the pipeline may use this signal to release the LSU stall. This module does not encode exception-completion information in lsu_unstall; exception information is provided by the separate exception output signals.

The byte-select signal dcpu_sel_o is determined jointly by lsu_op and the low two bits of the effective address dcpu_adr_o[1:0]. It is used to select the valid byte lanes on the 32-bit data bus. For byte store SB, and byte loads LBZ and LBS, the module selects one byte lane according to the low two address bits: when the low two bits are 00, it selects 1000; when they are 01, it selects 0100; when they are 10, it selects 0010; and when they are 11, it selects 0001. This indicates that the interface maps the four byte lanes in order from the most significant byte to the least significant byte.

For halfword store SH, and halfword loads LHZ and LHS, the module only produces a valid byte select for halfword-aligned addresses. When the low two address bits are 00, dcpu_sel_o is 1100, selecting the upper two bytes. When the low two address bits are 10, dcpu_sel_o is 0011, selecting the lower two bytes. If the low two address bits are 01 or 11, the access is a misaligned halfword access. In that case, except_align is asserted, dcpu_cycstb_o does not issue a data-side request, and dcpu_sel_o falls through to the default branch and outputs 0000.

For word store SW, and word loads LWZ and LWS, the module only produces a valid byte select for word-aligned addresses. When the low two address bits are 00, dcpu_sel_o is 1111, indicating that all four byte lanes of the 32-bit data bus are valid. If the low two address bits are not 00, the access is a misaligned word access. In that case, except_align is asserted, dcpu_cycstb_o does not issue a data-side request, and dcpu_sel_o falls through to the default branch and outputs 0000. For other unmatched operation types or illegal address combinations, dcpu_sel_o also outputs 0000.

Load data-format conversion is performed by the or1200_mem2reg submodule. This submodule receives the low two address bits dcpu_adr_o[1:0], the current LSU operation type lsu_op, and the 32-bit data returned from the data side dcpu_dat_i, and outputs the 32-bit register-side result lsu_dataout. According to the load type and the low address bits, it selects the correct byte, halfword, or word data from dcpu_dat_i and performs the required extension. For unsigned loads such as LBZ and LHZ, the result needs to be zero-extended. For signed loads such as LBS and LHS, the result needs to be sign-extended. For word loads, the full 32-bit data is returned. or1200_lsu itself does not directly implement these extension operations; it passes lsu_op, the low address bits, and the raw read data to or1200_mem2reg.

Store data-format conversion is performed by the or1200_reg2mem submodule. This submodule receives the low two address bits dcpu_adr_o[1:0], the current LSU operation type lsu_op, and the register-side input data lsu_datain, and outputs the data-side write data dcpu_dat_o. Its function is to adjust the register write data onto the correct byte lanes of the data bus according to the store type and address low bits. The actual byte lanes to be written are indicated by dcpu_sel_o, while dcpu_dat_o provides the corresponding write data for those lanes.

In the overall operation flow, when a load or store instruction is executed, the module first generates the effective address by adding addrbase and addrofs. It then checks, according to lsu_op and the low address bits, whether the current access satisfies the alignment requirement. If the access is a misaligned halfword or word access, except_align is asserted and dcpu_cycstb_o is suppressed, so the access is not sent to the data side. If the access is aligned, lsu_op is nonzero, and there are no blocking conditions such as du_stall or lsu_unstall, then dcpu_cycstb_o is asserted and the module issues an access to the data side, while outputting the access address, write enable, byte-select signal, and normal data access tag.

For store operations, or1200_reg2mem adjusts lsu_datain into the data-side format dcpu_dat_o according to the low two address bits and the store type, while dcpu_sel_o indicates the valid byte lanes. For load operations, the data returned from the data side, dcpu_dat_i, is sent into or1200_mem2reg, which converts it into the register-side output lsu_dataout according to the low two address bits and the load type. If the data side returns dcpu_rty_i while the current request is valid, the module asserts lsu_stall, indicating that the memory access needs to wait. If the data side returns dcpu_ack_i, the module asserts lsu_unstall, indicating that the access has been acknowledged and the LSU stall can be released. If the data side also returns error information, the module outputs the corresponding exception classification signal according to dcpu_err_i and dcpu_tag_i.

In summary, the core role of or1200_lsu is to translate the LSU operation encoding into the address, request, write enable, byte select, access tag, exception indication, and read/write data-alignment control required by the data-side interface. It uses combinational logic to generate the control signals between the LSU and the data cache or data memory interface, and relies on or1200_mem2reg and or1200_reg2mem to perform load and store data-format conversion. This module does not contain a complete memory transaction state machine; instead, it relies on the external data-side interface signals ack, retry, err, and tag to cooperate in completing the memory access flow.

Processing Flow

During a load or store operation, the module first forms the effective data address by adding `addrbase` and `addrofs`. The resulting address is driven to `dcpu_adr_o` and its low two bits are reused internally for alignment checking, byte-lane selection, and read/write data alignment.

After the effective address is generated, the module checks whether the access is properly aligned according to `lsu_op`. Byte accesses are allowed at any byte address. Halfword accesses must have address bit 0 cleared, and word accesses must have address bits [1:0] equal to `00`. If the access is misaligned, `except_align` is asserted and the outgoing data-side request `dcpu_cycstb_o` is suppressed.

If the access is aligned, the module determines whether a data-side request should be issued. `dcpu_cycstb_o` is asserted only when `lsu_op` is nonzero and none of the blocking conditions `du_stall`, `lsu_unstall`, or `except_align` is asserted. At the same time, the module drives `dcpu_we_o` from `lsu_op[3]`, generates `dcpu_sel_o` from `lsu_op` and the low address bits, and outputs `OR1200_DTAG_ND` on `dcpu_tag_o` for an active request. When no request is active, `dcpu_tag_o` is set to `OR1200_DTAG_IDLE`.

For store operations, the register-side write data `lsu_datain` is passed to `or1200_reg2mem`. This submodule uses the low two address bits and `lsu_op` to place the store data onto the correct byte lanes of `dcpu_dat_o`. The corresponding valid byte lanes are indicated by `dcpu_sel_o`.

For load operations, the data returned from the data side on `dcpu_dat_i` is passed to `or1200_mem2reg`. This submodule uses the low two address bits and `lsu_op` to extract the selected byte, halfword, or word and to generate the 32-bit register-side result `lsu_dataout`, including the required sign or zero extension for narrow loads.

While a request is active, if the data side asserts `dcpu_rty_i`, the module asserts `lsu_stall`, indicating that the pipeline should continue waiting for the memory access. When the data side asserts `dcpu_ack_i`, the module asserts `lsu_unstall`, indicating that the access has been acknowledged and the LSU stall can be released.

If the data side reports an error through `dcpu_err_i`, the module classifies the error by decoding `dcpu_tag_i`. A tag value of `OR1200_DTAG_TE` produces `except_dtlbmiss`, a tag value of `OR1200_DTAG_PE` produces `except_dmmufault`, and a tag value of `OR1200_DTAG_BE` produces `except_dbuserr`. These exception outputs are combinational classifications of the downstream response.
